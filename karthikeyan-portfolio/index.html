Engineering beyond code

I'm a Team Lead and Senior Software Engineer working on business software where the hard part is rarely the code itself. It's getting the requirement right, modelling the domain so the workflow holds up, and making sure the system behaves correctly when real users and real data arrive.

Most of my work sits between the business and the codebase: turning evolving requirements into architecture, keeping business rules explicit and validated, and making testing, security and deployment part of the work rather than an afterthought. I lead and mentor developers through that same process — planning, reviewing, and shipping together.

Lately I'm applying AI coding agents and context engineering inside that discipline, to see where they genuinely make a team faster without lowering the bar.

Exploring AI-native engineering

AI should not replace engineering discipline. It should amplify it.

How I approach working with coding agents: the agent does more of the typing, but the engineering process around it stays intact. Select a stage to see what happens there.

Start from a scoped task

An agent gets a clear goal, constraints and a definition of done — the same thing a developer would need — not a vague prompt.

Give the agent the system, not just the prompt

Output quality tracks context quality. The agent needs the parts of the system that matter for this change:

  • Codebase
  • Database schema
  • Requirements
  • Documentation
  • Tests
  • APIs
  • Architecture rules

Plan before code

The agent proposes an approach first. The plan is checked against the requirement and the architecture rules before anything is written.

Small, traceable changes

Implementation follows existing conventions and stays reviewable. Large, sweeping diffs are a signal to stop and re-plan.

Same bar as human-written code

Automated tests run on every change. Agent-written code doesn't get a lighter test suite.

Evaluate against the business rule

Passing tests isn't the finish line. Output is checked against business rules, edge cases and security expectations.

An engineer owns the decision

A person reads the diff, understands it and is accountable for what merges. This step is never automated away.

Ship through the normal pipeline

The change goes through the same CI/CD, environments and rollback plan as everything else.
